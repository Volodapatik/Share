# QR-Bridge

Експериментальна **клієнтська** (без бекенду) платформа для передачі файлів між
двома смартфонами через оптичний канал — потік QR-кодів, що швидко змінюються
на екрані одного пристрою й зчитуються камерою іншого.

Використовує спрощений **систематичний fountain-код** (у дусі Luby Transform /
подібно до проєктів на кшталт `txqr`), тому втрачені або задубльовані кадри
не зупиняють передачу — приймач просто чекає, доки не набереться достатньо
"корисних" кадрів, щоб відновити файл повністю.

## Як це працює коротко

1. **Відправник** ділить файл на `K` блоків фіксованого розміру.
2. Перші `K` кадрів — це самі блоки без змін (систематична частина).
3. Далі йдуть нескінченні "repair"-кадри: XOR кількох випадково (але
   детерміновано, за seed = sessionId+esi) обраних блоків.
4. Кожен кадр кодується у QR у byte-mode (сирі байти, без base64), з
   компактним заголовком (сесія, номер кадру, кількість блоків, розмір блоку).
5. **Приймач** сканує камерою, парсить заголовок, XOR-ить символ із уже
   відомими блоками (peeling-декодер) — і поступово "розплутує" всі `K`
   блоків, навіть якщо частина кадрів не була зчитана.
6. Окремі "meta"-кадри (кожен 8-й) несуть ім'я файлу, MIME-тип, точний
   розмір і CRC32 для перевірки цілісності.
7. Коли всі блоки відновлені й контрольна сума збігається — файл автоматично
   зберігається (download) на приймачі.

## Структура проєкту

```
qr-bridge/
├── index.html   — розмітка, перемикач Sender/Receiver, панелі статистики
├── style.css    — мобільний темний інтерфейс
├── app.js       — вся логіка: кодек кадрів, fountain-код, генерація QR, сканування
└── README.md
```

Зовнішні залежності підключаються з CDN прямо в `index.html` (окремих
збірок/npm не потрібно):
- [`qrcode`](https://github.com/soldair/node-qrcode) — генерація QR (byte-mode, canvas)
- [`jsQR`](https://github.com/cozmo/jsQR) — сканування/декодування QR з камери

## Розгортання

### GitHub Pages
1. Створіть репозиторій і закиньте туди 3 файли (`index.html`, `style.css`, `app.js`).
2. Settings → Pages → Deploy from branch → `main` / `root`.
3. Відкрийте видану GitHub-адресу на обох телефонах (HTTPS обов'язковий —
   без нього браузер не дасть доступу до камери).

### Локально
Камера в мобільних браузерах вимагає HTTPS **або** `localhost`. Найпростіше:

```bash
# python 3
python3 -m http.server 8000
```

і відкрити `http://<IP-комп'ютера>:8000` — але для доступу до камери на
телефоні знадобиться або тунель (ngrok/cloudflared), або HTTPS-сертифікат,
оскільки звичайний `http://IP` браузер камеру не дасть.

Найшвидший варіант для тесту з двох телефонів — саме **GitHub Pages** (крок
вище) або будь-який інший статичний HTTPS-хостинг (Netlify, Vercel, Surge).

## Використання

1. На одному телефоні відкрийте застосунок → вкладка **«Відправник»** →
   оберіть файл → «Почати трансляцію».
2. На другому телефоні → вкладка **«Отримувач»** → «Увімкнути камеру» →
   наведіть на екран першого телефона так, щоб QR-код повністю потрапляв у
   кадр.
3. Стежте за панеллю статистики (FPS / КБ/с / прогрес / таймер) і бейджем
   `СИНХРОНІЗОВАНО`. Коли прогрес приймача досягне 100% і контрольна сума
   збіжиться — файл автоматично завантажиться.

## Параметри та тюнінг

- **Розмір блоку** — більший блок = менше кадрів потрібно, але щільніший і
  важчий для сканування QR. Якщо камера погано ловить кадри — зменшіть блок.
- **FPS кадрів** — реальна частота обмежена швидкістю рендеру `qrcode.js` і
  частотою оновлення екрана; 15–24 fps зазвичай надійніший компроміс, ніж 60.
- Якщо між пристроями сильно різна освітленість/відстань — зменшіть FPS і/або
  розмір блоку для стабільнішого зчитування камерою.

## Відомі обмеження (це прототип / PoC)

- Розподіл ступеня fountain-коду спрощений (не строгий Robust Soliton) —
  достатній для демонстрації, але не оптимальний за кількістю зайвих кадрів.
- Немає адаптивного авто-підбору розміру блоку/FPS залежно від якості камери.
- Швидкість реально обмежена продуктивністю мобільного браузера при
  рендерингу/декодуванні QR, а не лише вибраним FPS.
- Перевірено логічно, але **не тестувалося наживо в браузері** (середовище
  розробки без мережевого доступу) — перед використанням варто прогнати
  на реальних пристроях і за потреби скоригувати розмір блоку/FPS.
